# 用户信息传递方案设计

## 概述

客户端请求携带的是"凭证"（Token）：这是一个由 Sa-Token 生成的、有时效性的字符串，代表了用户的登录状态。

- **网关负责"验证凭证，签发信任"**：网关作为唯一入口，负责校验这个 Token 的真伪。验证通过后，它会提取出最核心的用户身份信息（如 userId），并将其放入一个自定义的请求头（如 X-User-ID）中。这个新的请求头，就是网关签发给下游服务的"信任状"。
- **下游服务只认"信任状"**：下游的微服务不再关心原始的 Token 是什么，也无需集成 Sa-Token 进行重复校验。它们只需要无条件信任来自网关的请求头 X-User-ID，并以此为基础构建当前请求的用户上下文。

这样做的好处是显而易见的：

- **职责分离**：网关专注安全，服务专注业务。
- **性能提升**：避免了在每个微服务中都去 Redis 查询 Token 有效性的重复开销。
- **技术解耦**：下游服务甚至可以不用 Java，只要能读取 HTTP 请求头即可。

## 技术选型与组件职责

| 组件 | 技术选型 | 核心职责 |
|------|----------|----------|
| API 网关 | Spring Cloud Gateway | 1. 接收所有外部请求。<br>2. 集成 Sa-Token，调用 StpUtil.checkLogin() 完成 Token 校验。<br>3. 从 Sa-Token 上下文中获取 userId。<br>4. 将 userId 注入到新请求头 X-User-ID 中，并转发给下游服务。 |
| 认证服务 | Spring Boot + Sa-Token | 1. 提供 /login 等接口，处理用户名密码校验。<br>2. 校验成功后，调用 StpUtil.login(userId)，由 Sa-Token 生成 Token 并存入 Redis。 |
| 业务服务 | Spring Boot + Sa-Token（可选） | 1. 提供一个拦截器（Interceptor/Filter）。<br>2. 拦截器从请求头中读取 X-User-ID。<br>3. 调用 StpUtil.login(userId) 在当前线程建立一个临时的登录上下文，使业务代码能通过 StpUtil.getLoginId() 方便地获取用户 ID。 |
| 共享存储 | Redis | 作为 Sa-Token 的后端存储，持久化 Token 与用户会话信息的映射关系，实现分布式会话共享。 |

## 详细交互流程

我们可以将整个流程分为登录和访问两个阶段。

### 登录阶段：获取"通行证"

1. 客户端向认证服务发送登录请求（包含用户名和密码）。
2. 认证服务验证凭据正确后，执行 StpUtil.login(userId)。
3. Sa-Token 会生成一个唯一的 Token，并将用户会话信息（以 userId 为核心）存入 Redis。
4. 认证服务将这个 Token 返回给客户端。

### 访问阶段：凭证校验与身份传递

1. 客户端发起业务请求，在请求头中携带 Token，例如 `satoken: <token_value>`。
2. API 网关拦截请求，Sa-Token 自动从请求头中读取 Token，并通过 StpUtil.checkLogin() 去 Redis 中验证其有效性。
3. 验证成功：网关从 Sa-Token 的上下文中拿到 userId。
4. 身份注入：网关使用 ServerWebExchange 的 mutate() 方法，创建一个新的请求，并添加一个自定义请求头 `X-User-ID: <userId>`，然后将请求转发给下游的订单服务。
5. 订单服务收到请求，其内部的拦截器会从请求头中读取 X-User-ID 的值。
6. 建立上下文：拦截器调用 StpUtil.login(userId)。注意，这并非真正的登录，而是利用 Sa-Token 的 API 在当前线程中快速建立一个登录态，使得后续的业务代码可以无缝地使用 StpUtil.getLoginId() 来获取当前用户 ID。

## 关键设计细节与优势

### 下游服务零依赖原始 Token

下游服务完全不需要知道客户端传来的原始 Token 是什么格式，也不需要引入 Sa-Token 的复杂配置来解析它。它只需要一个简单的拦截器来读取 X-User-ID 即可，这使得业务服务非常纯粹。

### 解决了服务间调用的身份传递问题

当订单服务需要通过 Feign 调用库存服务时，身份不会丢失。我们只需配置一个 Feign 拦截器，它会自动从当前线程的上下文（即上一步建立的登录态）中获取 userId，并将其放入新的 Feign 请求的 X-User-ID 请求头中。这样，无论调用链多深，用户身份都能被准确传递。

### 安全性更高

原始的 Token 只在网关处暴露一次。在内网的服务间通信中，传递的是经过网关验证后的 userId，即使内网被窃听，攻击者拿到的也只是用户 ID，而无法伪造一个有效的 Sa-Token，因为 Token 的签名密钥只在认证服务和网关手中。

## 数据模型设计

### Redis 中 Token 存储模型

Sa-Token 在 Redis 中存储的主要数据结构如下：

| 键名格式 | 类型 | 说明 | 示例 |
|---------|------|------|------|
| `satoken:login:token:<token_value>` | String | 存储 Token 与用户 ID 的映射关系 | `satoken:login:token:abc123` → `1001` |
| `satoken:login:user:<user_id>` | String | 存储用户当前有效的 Token | `satoken:login:user:1001` → `abc123` |
| `satoken:login:timeout:<token_value>` | String | 存储 Token 的过期时间（时间戳） | `satoken:login:timeout:abc123` → `1704067200000` |
| `satoken:login:info:<token_value>` | Hash | 存储用户的会话信息（可选） | `satoken:login:info:abc123` → `{"role":"admin", "nickname":"张三"}` |

### 核心数据结构

1. **Token 结构**
   - 格式：由 Sa-Token 生成的唯一字符串
   - 长度：默认 32 字符（可配置）
   - 组成：随机字符串 + 时间戳 + 签名

2. **用户身份信息**
   - `userId`：用户唯一标识（如自增 ID 或 UUID）
   - 类型：String/Number
   - 示例：`1001`、`user_123456`

3. **请求头信息**
   - `satoken`：客户端请求携带的原始 Token
   - `X-User-ID`：网关注入的用户身份标识
   - 格式：`X-User-ID: <userId>`

4. **会话上下文**
   - 存储于：业务服务的线程本地变量（ThreadLocal）
   - 内容：当前请求的用户 ID 及相关信息
   - 作用：使业务代码可通过 `StpUtil.getLoginId()` 直接获取用户身份

### 数据流转过程

1. **登录时**：
   - 认证服务生成 Token 并存储到 Redis
   - 建立 `token → userId` 和 `userId → token` 的双向映射
   - 设置 Token 过期时间

2. **访问时**：
   - 网关验证 Token 有效性（检查 Redis 中是否存在）
   - 从 Redis 中获取 userId
   - 将 userId 注入到请求头中转发

3. **服务间调用时**：
   - Feign 拦截器从当前会话上下文获取 userId
   - 将 userId 注入到新请求的 `X-User-ID` 头中

4. **Token 过期/注销时**：
   - 从 Redis 中删除对应的 Token 相关键值
   - 清除用户与 Token 的映射关系
