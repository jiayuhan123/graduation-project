# 毕业设计：微服务项目技术选型与中间件部署说明

本项目针对高并发、高可用和现代化微服务架构的需求，进行了前瞻性的技术选型，并在 4核4G 的测试服务器上完成了轻量化、内存优化版的容器化部署。本文档用于记录项目技术选型依据、中间件配置及连接凭证，可直接作为毕业设计论文“系统设计与实现”部分的素材。

---

## 一、 核心开发技术选型

为了保证本项目的技术前瞻性与先进性，本项目选择拥抱最新的 LTS 长期支持版 JDK 21 平台与下一代 Spring 框架体系：

| 技术组件 | 选定版本 | 选型依据与优势 |
| :--- | :--- | :--- |
| **JDK** | **JDK 21 LTS** | 现代化长期支持版。拥有极其成熟的**虚拟线程 (Virtual Threads)** 支持，采用轻量级协程模型替代传统线程池，大幅降低 I/O 密集型微服务的高并发开销。 |
| **Spring Boot** | **4.0.x** | 基于 Spring Framework 7 和 Jakarta EE 11 构建，最低 JDK 要求为 17，能完美运行在 JDK 21 上。彻底抛弃了历史遗留的 `javax` 命名空间，底层依赖库深度优化，内存占用更低，启动速度更快。 |
| **Spring Cloud** | **2025.1.x (Oakwood)** | 最新稳定版微服务治理工具链，为服务间调用、动态路由、负载均衡提供基础支持。 |
| **Spring Cloud Alibaba** | **2025.1.0.0** | 针对 Spring Boot 4.0.x 进行深度适配的阿里开源微服务组件，提供 Nacos（注册与配置中心）、Sentinel（流量治理，仅作为代码依赖集成，暂不部署可视化控制台）、Seata（分布式事务）的无缝集成。 |

## 三、 内存极限压缩策略 (针对 4C4G 服务器)

在微服务场景中，多服务、多连接极易引发服务器 OOM。本项目在部署阶段实施了以下深度优化方案，将中间件总内存开销从默认的 **2G+** 压缩至 **1.1G 左右**，为 Java 业务服务腾出了 **2.5G+** 的安全空间：

### 1. 数据库与缓存优化
*   **MySQL 8.4 瘦身**：
    *   关闭性能分析器：`--performance_schema=OFF`（核心瘦身项，直接节省 100MB+ 内存）。
    *   限制 InnoDB 缓冲池大小：`--innodb_buffer_pool_size=64M`（默认 128M）。
    *   限制最大连接数：`--max_connections=50`，防微服务连接暴涨。
*   **Redis 8.0 限制**：
    *   限制最大内存上限：`--maxmemory 96mb`。
    *   内存淘汰策略：`--maxmemory-policy allkeys-lru`，防止内存无限增长。

### 2. Java 虚拟机 (JVM) 调优
*   **Nacos 3.2.2 限制**：
    *   强制指定堆内存：`-Xms256m -Xmx256m -Xmn128m`。
    *   **架构简化**：采用**内嵌 Derby 数据库**模式运行，免去了 Nacos 连接外部 MySQL 数据库的额外开销与建表初始化配置，开发测试阶段更加轻量。
> 📌 **Sentinel 备注**：Sentinel 官方已停止维护 Docker 镜像，社区镜像最高仅至 1.8.6。后期业务代码将直接引入 Sentinel 依赖包实现限流熔断功能，暂不部署可视化控制台。

### 3. 消息队列与对象存储调优
*   **RabbitMQ 内存控制**：
    *   物理内存上限限制为 `350MB`。由于新版本废弃了环境变量水位线配置，此处依赖 Docker 容器原生的资源隔离机制。
*   **MinIO 协程限制**：
    *   限制容器物理内存为 `256MB`。
    *   设置环境变量 `GOMAXPROCS=2`，限制 Go 语言并发运行时使用的 CPU 核心数，降低内存波动。
