# 技术选型说明

> **文档版本**：v2.0.0 | **最后更新**：2026-08-06 | **状态**：已完成

---

## 1. 概述

本文档说明毕业设计微服务基础框架各技术组件的选型理由，为新选题的技术决策提供依据。所有技术选型均以**工程适用性**、**生态活跃度**、**学习价值**和**企业实践主流程度**为核心评估维度。

---

## 2. 编程语言与运行时

### 2.1 JDK 21（LTS）

| 对比维度 | JDK 17 | **JDK 21（选用）** | JDK 22+ |
|----------|--------|-------------------|---------|
| 支持类型 | LTS | **LTS（长期支持）** | 非LTS |
| 虚拟线程 | 预览特性 | **正式发布（Project Loom）** | 稳定 |
| 模式匹配 | 部分支持 | **完整支持** | 完整支持 |
| Spring Boot 支持 | ✅ | **✅ 官方推荐** | ✅ |

**选型理由**：
- JDK 21 是 Java 目前最新的 LTS（长期支持）版本，企业生产环境迁移首选目标；
- **虚拟线程（Virtual Threads）** 正式发布，与 Spring Boot 4.x 深度集成，大幅提升 I/O 密集型应用的吞吐量，对微服务场景尤为有利；
- 相比 JDK 17，JDK 21 在序列化、模式匹配等方面有进一步改进，且 Spring Boot 4.x 最低要求 JDK 17，选用 JDK 21 更具前瞻性；
- 具备较高的论文和面试价值，体现对新技术的掌握能力。

## 3. 核心框架

### 3.1 Spring Boot 4.0.6

| 对比维度 | Spring Boot 2.x | Spring Boot 3.x | **Spring Boot 4.x（选用）** |
|----------|-----------------|-----------------|---------------------------|
| JDK 要求 | JDK 8+ | JDK 17+ | **JDK 21+** |
| Jakarta EE | ❌ javax | ✅ jakarta | **✅ jakarta** |
| GraalVM 原生镜像 | 有限支持 | 正式支持 | **增强支持** |
| 虚拟线程支持 | ❌ | 实验性 | **深度集成** |
| 安全框架 | Spring Security 5 | Spring Security 6 | **Spring Security 7** |

**选型理由**：
- Spring Boot 4.x 是当前（2025年）最新主线版本，代表 Spring 生态最新设计理念；
- 全面迁移至 `jakarta.*` 命名空间，与 Java EE 历史包袱彻底脱离；
- 对 JDK 21 虚拟线程的深度支持，使得在高并发场景下能充分发挥 JDK 21 的性能优势；
- 作为毕业设计，选用最新稳定版本能体现技术追踪能力。

### 3.2 Spring Cloud 2025.1.1

Spring Cloud 2025.1.1 是与 Spring Boot 4.x 配套的 Spring Cloud 版本，采用日历化版本命名规范（`年份.次要版本.补丁版本`）。

**选型理由**：与 Spring Boot 4.0.x 严格对应，确保依赖兼容性。

### 3.3 Spring Cloud Alibaba 2025.1.0.0

Spring Cloud Alibaba 是阿里巴巴开源的 Spring Cloud 扩展，提供 Nacos、Sentinel、RocketMQ 等组件的 Spring Cloud 集成。

**选型理由**：
- 提供对 Nacos（注册中心 + 配置中心）的开箱即用支持；
- 阿里巴巴双十一亿级流量验证，工程可靠性高；
- 国内企业广泛使用，具有较高的就业市场价值。

## 4. 网关层

### 4.1 Spring Cloud Gateway（WebFlux 响应式）vs Zuul

| 对比维度 | Netflix Zuul 1.x | Netflix Zuul 2.x | **Spring Cloud Gateway（选用）** |
|----------|-----------------|-----------------|----------------------------------|
| I/O 模型 | 同步阻塞（Servlet） | 异步非阻塞 | **异步非阻塞（WebFlux/Reactor）** |
| 性能 | 较低（线程池模型） | 较高 | **高（事件循环模型）** |
| Spring 原生支持 | 需要额外集成 | 需要额外集成 | **Spring 官方维护** |
| 维护状态 | Netflix 已停止维护 | Netflix 已停止维护 | **活跃维护** |
| 编程模型 | 命令式 | 响应式 | **响应式（WebFlux）** |
| 过滤器机制 | ZuulFilter | ZuulFilter | **GatewayFilter** |

**选型理由**：
1. **性能优势**：Spring Cloud Gateway 基于 Reactor Netty，采用事件驱动的非阻塞 I/O 模型，在相同硬件资源下吞吐量显著高于 Zuul 1.x；
2. **官方维护**：Zuul 的 Netflix 团队已将其置于维护模式，Spring Cloud Gateway 是 Spring 官方的替代方案，生命周期有保障；
3. **与 Spring 生态深度集成**：原生支持 Spring Security、Spring Cloud LoadBalancer 等组件；
4. **WebFlux 一致性**：网关采用响应式编程模型，与 JDK 21 虚拟线程协同，最大化 I/O 性能。

> **注意**：本项目使用 `spring-cloud-starter-gateway-server-webflux` 依赖，基于 WebFlux 响应式编程模型，鉴权过滤器、路由配置均采用响应式写法（返回 `Mono<Void>`）。

## 5. 服务注册与配置中心

### 5.1 Nacos 3.2.2 vs 竞品对比

| 对比维度 | Eureka | Consul | **Nacos（选用）** | ZooKeeper |
|----------|--------|--------|------------------|-----------|
| 功能 | 仅注册中心 | 注册+配置+健康检查 | **注册+配置+健康检查** | 注册中心 |
| CAP 模型 | AP | CP | **AP（注册）+CP（配置）** | CP |
| 维护状态 | Netflix 已停止维护 | 活跃维护 | **活跃维护（阿里开源）** | 活跃维护 |
| 配置热更新 | 需配合 Config 服务 | 支持 | **支持（推送模式）** | 支持 |
| 控制台 UI | 无 | 有 | **功能完善** | 无（第三方） |
| Spring Cloud 集成 | 官方支持 | 官方支持 | **Spring Cloud Alibaba 原生支持** | 第三方 |

**选型理由**：
1. **一体化能力**：Nacos 同时承担服务注册发现和配置中心两个职责，相比 Eureka（注册）+ Spring Cloud Config（配置）的组合方案，减少了中间件数量和运维复杂度；
2. **AP+CP 灵活切换**：注册中心采用 AP 模型保证可用性，配置中心采用 CP 模型保证一致性，满足不同场景需求；
3. **配置热更新**：Nacos 支持配置变更后自动推送到各服务，实现不停机热更新，Eureka 本身不具备此能力；
4. **国内生态**：配合 Spring Cloud Alibaba 使用，文档资料丰富，企业实践案例多。

#### Nacos DataID 配置规范
本项目各服务配置文件存储在 Nacos，DataID 格式为：

```
${spring.application.name}.yaml
```

例如：
- `gateway.yaml` → 网关服务配置
- `user-service.yaml` → 用户服务配置

## 6. ORM 框架

### 6.1 MyBatis-Plus vs JPA（Hibernate）

| 对比维度 | JPA/Hibernate | Spring Data JPA | **MyBatis-Plus（选用）** |
|----------|---------------|-----------------|--------------------------|
| SQL 控制 | 自动生成（HQL/JPQL） | 自动生成 | **手写 SQL + 自动生成** |
| 性能调优 | 复杂（N+1 问题） | 复杂 | **直观，SQL 可见** |
| 学习曲线 | 陡峭（实体关系映射） | 中等 | **平缓** |
| 复杂查询 | 需要原生 SQL | 限制多 | **灵活（XML/注解）** |
| 逻辑删除 | 需手动实现 | 需手动实现 | **内置支持（@TableLogic）** |
| 代码生成 | 支持 | 支持 | **代码生成器完善** |
| 国内使用率 | 中 | 中 | **非常高** |

**选型理由**：
1. **SQL 透明可控**：MyBatis-Plus 在 MyBatis 基础上增强，SQL 语句清晰可见，性能问题易于排查和优化；
2. **内置增强功能**：提供逻辑删除（`@TableLogic`）、自动填充（`@TableField(fill=...)`）、乐观锁（`@Version`）等开箱即用的功能，减少样板代码；
3. **条件构造器**：`QueryWrapper`/`LambdaQueryWrapper` 提供类型安全的 Lambda 条件构造，避免字符串拼写错误；
4. **分页插件**：内置 `PaginationInnerInterceptor`，统一分页实现；
5. **与 Spring Boot 集成成熟**：依赖配置简单，文档完善。

## 7. 鉴权框架

### 7.1 Sa-Token vs Spring Security vs JWT-only

| 对比维度 | JWT 纯手写 | Spring Security | **Sa-Token（选用）** |
|----------|-----------|-----------------|---------------------|
| 配置复杂度 | 低（但功能少） | 高 | **低** |
| 功能完整性 | 基础 | 完整 | **完整（踢人下线、多端登录等）** |
| 学习曲线 | 低 | 陡峭 | **平缓** |
| 与 WebFlux 兼容 | 需适配 | 支持（Spring Security Reactive） | **支持（sa-token-reactor）** |
| Redis 集成 | 手动实现 | 手动实现 | **开箱即用** |
| 踢人下线 | 复杂实现 | 复杂实现 | **内置 API** |
| 国内文档 | 少 | 多 | **非常丰富** |

**选型理由**：
1. **轻量易用**：Sa-Token 相比 Spring Security 配置极为简洁，适合毕业设计快速实现安全功能；
2. **功能丰富**：内置登录认证、踢人下线、账号封禁、角色权限认证、Session 管理等企业常用功能；
3. **Redis 集成**：原生支持将 Token 存储至 Redis，实现分布式会话共享；
4. **WebFlux 支持**：提供 `sa-token-reactor` 模块，与网关的 WebFlux 环境无缝兼容。

## 8. 缓存

### 8.1 Redis 8.0

**选型理由**：
- Redis 是目前业界最主流的内存数据库，用于 Token 存储（Sa-Token）、热点数据缓存、分布式锁等场景；
- Redis 8.0 引入了多项性能优化和新数据结构；
- 与 Spring Data Redis 深度集成，`RedisTemplate` / `@Cacheable` 开箱即用。

## 9. 消息队列

### 9.1 RabbitMQ vs Kafka vs RocketMQ

| 对比维度 | **RabbitMQ（选用）** | Kafka | RocketMQ |
|----------|---------------------|-------|---------|
| 消息模型 | AMQP，Exchange/Queue | 发布订阅（分区日志） | 发布订阅 |
| 延迟 | 低（毫秒级） | 较高（毫秒~秒） | 低 |
| 消息积压 | 有限（内存/磁盘） | 强（日志存储） | 强 |
| 部署复杂度 | **简单** | 需 ZooKeeper/KRaft | 中等 |
| 管理界面 | **management 插件** | 第三方 | RocketMQ Console |
| 适用场景 | **任务队列、异步解耦** | 日志、大数据流 | 金融、高可靠 |

**选型理由**：
1. **部署简单**：单节点 RabbitMQ 即可满足毕业设计需求，Docker 镜像 `management` 版本内置 Web 管理界面；
2. **适合异步解耦**：新业务中的通知、审核、订单状态变更等异步任务适合 RabbitMQ 的任务队列模型；
3. **Spring AMQP 集成**：`spring-boot-starter-amqp` 提供完整的 Spring 集成支持。

## 10. 对象存储

### 10.1 MinIO vs 阿里云 OSS vs FastDFS

| 对比维度 | **MinIO（选用）** | 阿里云 OSS | FastDFS |
|----------|-----------------|-----------|---------|
| 部署方式 | **私有化部署** | 云服务（付费） | 私有化部署 |
| S3 兼容性 | **完全兼容 S3 API** | 兼容 S3 | 不兼容 |
| 性能 | **高** | 高 | 中 |
| 运维成本 | **低（Docker 一键启动）** | 无需运维 | 中等 |
| 费用 | **免费（自托管）** | 按量付费 | 免费 |

**选型理由**：
1. **私有化部署**：毕业设计使用自建服务器，MinIO 可在 Docker 中一键启动，无需云服务费用；
2. **S3 API 兼容**：MinIO 完全兼容 Amazon S3 API，SDK 通用，未来如需迁移至云存储成本极低；
3. **高性能**：MinIO 在单机环境下读写性能优秀，能够满足头像、图片和业务附件等对象存储需求。

## 11. 容器化部署

### 11.1 Docker Compose

**选型理由**：
- 当前中间件（PostgreSQL、Redis、Nacos、RabbitMQ、Jenkins）通过 Docker Compose 统一编排，实现环境的**一键启动**和**版本锁定**；MinIO 保留为候选技术，按新选题需要再加入；
- 相比手动安装，Docker Compose 大幅降低环境配置复杂度，保证开发和生产环境一致性；
- 对于单服务器部署场景，Docker Compose 是比 Kubernetes 更轻量的选择。
