# 接口规范说明

> **文档版本**：v2.0.0 | **最后更新**：2026-08-06 | **状态**：已完成

---

## 1. 概述

本文档定义了本项目所有微服务接口的统一规范，包括响应格式、状态码体系、请求头规范、分页规范等。所有服务开发人员必须遵守此规范，确保接口风格一致性。

---

## 2. 统一响应格式

### 2.1 响应结构定义

所有接口均返回统一的 JSON 格式：

```json
{
    "code": 200,
    "message": "操作成功",
    "data": { ... }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | Integer | 业务状态码（非 HTTP 状态码） |
| `message` | String | 结果描述信息 |
| `data` | Object/Array/null | 响应数据，失败时为 `null` |

### 2.2 Result 泛型包装类

```java
package xyz.jiayuhan.common.result;

import lombok.Data;

/**
 * 统一响应结果包装类
 *
 * @param <T> 响应数据类型
 */
@Data
public class Result<T> {
    
    /**
     * 业务状态码
     */
    private Integer code;
    
    /**
     * 描述信息
     */
    private String message;
    
    /**
     * 响应数据
     */
    private T data;
    
    // 成功（有数据）
    public static <T> Result<T> success(T data) {
        Result<T> result = new Result<>();
        result.setCode(200);
        result.setMessage("操作成功");
        result.setData(data);
        return result;
    }
    
    // 成功（无数据）
    public static Result<Void> success() {
        return success(null);
    }
    
    // 失败（指定错误码）
    public static <T> Result<T> fail(Integer code, String message) {
        Result<T> result = new Result<>();
        result.setCode(code);
        result.setMessage(message);
        result.setData(null);
        return result;
    }
    
    // 失败（使用错误码枚举）
    public static <T> Result<T> fail(ResultCode resultCode) {
        return fail(resultCode.getCode(), resultCode.getMessage());
    }
}
```

### 2.3 响应示例

**成功响应（有数据）**：
```json
{
    "code": 200,
    "message": "操作成功",
    "data": {
        "id": 1001,
        "username": "resident001",
        "phone": "138****8000"
    }
}
```

**成功响应（无数据）**：
```json
{
    "code": 200,
    "message": "操作成功",
    "data": null
}
```

**失败响应**：
```json
{
    "code": 400,
    "message": "用户名已存在",
    "data": null
}
```

## 3. 状态码规范

### 3.1 HTTP 状态码

所有接口的 HTTP 状态码**统一返回 200**（业务层面），仅在网络/框架级别使用其他 HTTP 状态码：

| HTTP 状态码 | 使用场景 |
|-------------|----------|
| 200 | 请求正常处理（包含业务失败的情况） |
| 401 | 网关鉴权失败（无效 Token）|
| 404 | 路径不存在（网关路由未匹配）|
| 500 | 服务器内部错误（未捕获异常）|

### 3.2 业务状态码（code 字段）

| 状态码 | 含义 | 说明 |
|--------|------|------|
| **200** | **操作成功** | 业务正常处理完成 |
| **400** | **请求参数错误** | 参数校验失败、格式错误等 |
| **401** | **未登录 / Token 无效** | 需要登录才能访问 |
| **403** | **无权限** | 已登录但无操作权限 |
| **404** | **资源不存在** | 查询的数据不存在 |
| **409** | **数据冲突** | 如：用户名已存在 |
| **429** | **请求过于频繁** | 触发限流 |
| **500** | **服务器内部错误** | 未预期的系统异常 |
| **503** | **服务暂不可用** | 服务维护中或下游服务不可用 |

**自定义业务错误码（4位数）**：

| 错误码 | 含义 |
|--------|------|
| 1001 | 用户名或密码错误 |
| 1002 | 用户名已存在 |
| 1003 | 手机号已存在 |
| 1004 | 账号已被禁用 |
| 1005 | 旧密码不正确 |
| 1101 | 社区不存在或已停用 |
| 1102 | 居民已加入该社区 |
| 1103 | 不属于该社区成员 |
| 1201 | 纪念档案不存在 |
| 1202 | 纪念档案状态不允许操作 |
| 1203 | 无权限操作该档案 |
| 1204 | 留言内容含敏感词 |
| 1301 | 预约时段已满额 |
| 1302 | 该时段已存在预约 |
| 1303 | 预约状态不允许该操作 |
| 1304 | 预约时间已过，无法取消 |

## 4. 请求头规范

### 4.1 鉴权请求头

| 请求头名称 | 类型 | 必须 | 说明 |
|------------|------|------|------|
| `satoken` | String | 否（白名单接口） | 用户登录 Token，由登录接口颁发 |

**示例**：
```http
GET /api/user/info HTTP/1.1
Host: 122.51.234.113:10000
satoken: a1b2c3d4-e5f6-7890-abcd-ef1234567890
Content-Type: application/json
```

### 4.2 内部服务通信请求头

> **注意**：以下请求头由网关自动注入，客户端**不应手动设置**（网关会覆盖同名请求头）。

| 请求头名称 | 类型 | 说明 |
|------------|------|------|
| `X-User-ID` | Long (String) | 当前登录用户的 ID，由网关注入 |

### 4.3 Content-Type

| 场景 | Content-Type |
|------|-------------|
| JSON 请求体 | `application/json; charset=UTF-8` |
| 文件上传 | `multipart/form-data`（遗照、头像等图片） |
| 表单提交 | `application/x-www-form-urlencoded` |

## 5. 分页参数规范

### 5.1 请求参数

所有列表查询接口统一使用以下分页参数：

| 参数名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `page` | Integer | 1 | 当前页码，从 1 开始 |
| `size` | Integer | 10 | 每页条数，最大 100 |
| `orderBy` | String | `create_time` | 排序字段 |
| `orderDir` | String | `desc` | 排序方向：`asc`/`desc` |

**请求示例**：
```
GET /api/memorial/deceased/list?page=1&size=10&orderBy=create_time&orderDir=desc
```

### 5.2 分页响应格式

```json
{
    "code": 200,
    "message": "操作成功",
    "data": {
        "total": 100,
        "pages": 10,
        "current": 1,
        "size": 10,
        "records": [
            { ... },
            { ... }
        ]
    }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `total` | Long | 总记录数 |
| `pages` | Long | 总页数 |
| `current` | Long | 当前页码 |
| `size` | Long | 每页条数 |
| `records` | Array | 当前页数据列表 |

## 6. 接口版本管理

### 6.1 版本策略

| 策略 | 格式 | 示例 |
|------|------|------|
| URL 路径版本（推荐） | `/api/v{n}/...` | `/api/v2/user/info` |
| 请求头版本 | `API-Version: 2` | — |

### 6.2 版本升级规则

- **向后兼容的修改**（添加字段、新增可选参数）：不升级版本
- **不兼容的修改**（删除字段、修改字段类型、修改 URL 结构）：**必须升级版本**，旧版本保留一定过渡期

### 6.3 当前版本状态

| 接口版本 | 状态 | 说明 |
|----------|------|------|
| v1（默认，无前缀） | 🔄 开发中 | 当前主版本 |

> 📝 待补充：当接口发生不兼容变更时，在此记录版本升级历史。

## 7. 接口幂等性规范

> 📝 待补充：对于重要的写入操作（如祭扫预约提交、档案审核），需实现接口幂等性，防止重复提交。

**推荐实现方案**：客户端提交时携带 `Idempotency-Key` 请求头（UUID），服务端检查 Redis 中是否存在该 Key，存在则返回缓存结果，不存在则处理并缓存结果。
