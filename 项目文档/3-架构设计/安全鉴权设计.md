# 安全鉴权设计

## 1. 方案概述

系统使用 Sa-Token 管理登录会话，Redis 保存会话状态。外部请求统一经过 Gateway：网关负责 Token 基础校验，下游服务负责角色、权限和数据归属校验。

## 2. 登录流程

1. 客户端调用 `POST /api/user/login`。
2. `user-service` 校验用户名或手机号及 BCrypt 密码。
3. 校验成功后调用 `StpUtil.login(userId)` 签发 Token。
4. 客户端保存响应中的 `tokenName` 与 Token，并在后续请求头中携带。
5. 网关读取 Redis 中的会话，校验后再转发请求。

注册和登录接口位于白名单，其余业务接口默认需要登录。新增匿名接口时必须明确记录原因，并按最小范围配置路径和请求方法。

## 3. 分层职责

| 层级 | 职责 |
|---|---|
| 客户端 | 安全保存 Token、携带请求头、登录失效后清理状态 |
| Gateway | 校验登录状态、过滤伪造用户头、注入可信用户上下文 |
| 业务服务 | 校验角色、操作权限、资源归属和业务状态 |
| Redis | 保存会话、Token 映射和可撤销登录状态 |

网关鉴权不能替代服务内授权。任何修改、删除和管理类接口都应在服务内部再次确认当前用户是否有权操作目标资源。

## 4. 角色扩展

基础框架暂时返回默认角色 `user`。新选题确定后，应按业务需要设计角色和权限表，并遵循：

- 默认拒绝，明确授权。
- 普通用户与管理员接口分离。
- 角色只表示权限集合，不替代数据归属校验。
- 高风险操作记录审计日志。

## 5. 安全要求

- 密码仅保存 BCrypt 哈希，不可明文存储或记录日志。
- 登录失败统一提示“用户名或密码错误”，防止账号枚举。
- 网关转发前先删除客户端提交的用户身份请求头，再写入可信值。
- 生产环境使用 HTTPS，并通过环境变量或配置中心保存密钥。
- 对登录、验证码、上传等高频接口配置限流。
- Token 过期、退出和账号禁用后应及时失效。
