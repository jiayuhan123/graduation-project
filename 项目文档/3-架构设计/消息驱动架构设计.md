# 消息驱动架构设计

## 1. 目标

RabbitMQ 用于跨服务异步事件。当前发布者是 User Service，消费者是 Notification Service 和 Audit Service。系统采用“至少一次投递 + 消费幂等”，不宣传无法证明的全局“仅一次”。

## 2. 可靠发布

```text
用户业务事务
  ├─ 修改业务表
  └─ 写 sys_outbox_event（同一 PostgreSQL 事务）
          ↓
调度器 FOR UPDATE SKIP LOCKED 批量领取
          ↓ mandatory publish + Publisher Confirm
          ├─ 成功：PUBLISHED
          └─ 失败：指数退避；达到上限 FAILED
```

这样避免“业务已提交、进程却在发消息前崩溃”导致事件永久丢失。Broker 已确认但发件箱状态提交失败时会重复发布，所以所有消费者仍需幂等。

## 3. 拓扑

| 资源 | 名称 |
| --- | --- |
| 领域事件 Topic Exchange | `app.domain.events` |
| 死信 Direct Exchange | `app.dead-letter` |
| 注册路由键 | `user.registered` |
| 审计路由键 | `audit.operation` |
| 通知消费队列 / 死信队列 | `notification.user-registered.v1` / `notification.dead-letter.v1` |
| 审计消费队列 | `audit.user-registered.v1`、`audit.operation.v1` |
| 审计死信队列 | `audit.dead-letter.v1` |

公共模块只声明交换机和事件 DTO；消费者服务声明并维护自己的队列、绑定和死信策略。

## 4. 重试与幂等

- 消费失败自动重试 4 次，间隔按 1s、2s、4s 等增长，上限 10s。
- 重试耗尽后不重新入原队列，消息由 DLX 路由到对应死信队列。
- 通知表以 `source_event_id` 唯一，审计表以 `event_id` 唯一。
- 业务处理与幂等落库在同一事务；重复消息直接确认。

## 5. 运维

- 监控发件箱 `PENDING` 数量、最老等待时间和 `FAILED` 数量。
- `PUBLISHED` 默认保留 7 天后定时清理；`FAILED` 不自动删除，必须人工确认。
- 监控队列堆积、未确认数、消费者数、发布 Nack/Return 和死信数量。
- 重放前先修复根因并确认消费者幂等，不直接清空死信队列。
- 事件契约做向后兼容变更；破坏性变更使用新事件类型或新版本队列。
