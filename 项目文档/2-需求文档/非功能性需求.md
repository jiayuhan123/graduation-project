# 非功能性需求

> **文档版本**：v1.0.0 | **最后更新**：2026-06-07 | **状态**：已完成

---

## 1. 概述

非功能性需求（Non-Functional Requirements, NFR）定义了系统在功能之外的质量属性，包括性能、安全性、可用性、可维护性、可扩展性等。这些需求对系统整体架构设计具有决定性影响。

---

## 2. 性能需求

### 2.1 响应时间指标

| 接口类型 | 目标响应时间（P95） | 目标响应时间（P99） | 说明 |
|----------|---------------------|---------------------|------|
| 查询类（GET） | ≤ 200ms | ≤ 500ms | 读多写少场景，Redis 缓存加速 |
| 写入类（POST/PUT） | ≤ 500ms | ≤ 1000ms | 包含数据库写入 |
| 文件上传 | ≤ 3000ms | ≤ 5000ms | 受文件大小影响 |
| 鉴权验证（网关层） | ≤ 50ms | ≤ 100ms | Redis 查询，必须极快 |

### 2.2 并发处理能力

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 系统并发用户数 | ≥ 500 | 同时在线用户（毕业设计预期规模） |
| 峰值 QPS（每秒请求数） | ≥ 200 | 核心接口峰值处理能力 |
| 单接口响应成功率 | ≥ 99% | 正常流量下接口成功率 |

> **说明**：当前服务器配置为 4核4G，属于资源受限环境。上述指标以中小型应用负载为基准，不追求极限高并发。

### 2.3 数据量级规划

| 数据类型 | 预期规模 | 处理策略 |
|----------|----------|----------|
| 用户数据 | 万级（演示/测试） | MySQL 索引优化 + 分页查询 |
| 文件存储 | GB 级 | MinIO 对象存储，不占用 MySQL |
| 缓存数据 | MB 级 | Redis 设置 maxmemory + LRU 策略 |
| 消息队列积压 | 千级 | RabbitMQ 消费速率监控 |

## 3. 安全性需求

### 3.1 认证与授权

| 需求项 | 要求 | 实现方案 |
|--------|------|----------|
| 用户身份认证 | 所有需要鉴权的接口必须携带有效 Token | Sa-Token + Redis |
| Token 有效期 | Token 默认有效期 7 天，活跃用户自动续签 | Sa-Token 活跃超时机制 |
| 多端登录控制 | 支持配置同端互斥（踢下线）或允许多端同时在线 | Sa-Token 多端登录配置 |
| 权限校验 | 管理员接口需要校验用户角色 | Sa-Token @SaCheckRole 注解 |

### 3.2 数据安全

| 需求项 | 要求 | 实现方案 |
|--------|------|----------|
| 密码存储 | 用户密码必须使用 BCrypt 哈希加密存储，禁止明文 | Spring Security BCryptPasswordEncoder |
| 敏感信息脱敏 | 接口响应中手机号、邮箱需要脱敏处理（如：138****1234） | 自定义序列化脱敏 |
| SQL 注入防护 | 禁止拼接 SQL 字符串，使用 MyBatis-Plus 参数化查询 | MyBatis-Plus 框架保证 |
| XSS 防护 | 对用户输入内容进行 HTML 转义处理 | 全局过滤器 |

### 3.3 通信安全

| 需求项 | 要求 | 说明 |
|--------|------|------|
| 传输加密 | 生产环境启用 HTTPS（TLS 1.2+） | > 📝 待补充（证书配置） |
| 中间件访问控制 | MySQL/Redis/RabbitMQ 须设置强密码，不对外暴露端口 | Docker 网络隔离 |
| 接口限流 | 关键接口（登录/注册）设置频率限制，防止暴力破解 | 网关限流过滤器 |

### 3.4 日志与审计

| 需求项 | 要求 |
|--------|------|
| 操作日志 | 记录用户登录、重要操作的时间、IP 来源 |
| 异常日志 | 所有未捕获异常必须记录完整堆栈信息 |
| 日志级别 | 生产环境使用 INFO 级别，开发环境使用 DEBUG |

## 4. 可用性需求

### 4.1 系统可用性目标

| 场景 | 可用性目标 | 说明 |
|------|-----------|------|
| 核心服务（网关+用户服务） | ≥ 99% | 月允许停机时间约 7 小时 |
| 整体系统 | ≥ 95% | 单服务器部署，停机维护可接受 |

> **注意**：当前单服务器部署方案本身不具备高可用性（无冗余节点）。上述目标以正常运行（无故障）为前提，不考虑服务器硬件故障场景。若需提升可用性，需引入多节点部署。

### 4.2 故障恢复

| 故障类型 | 处理策略 | 恢复时间目标（RTO） |
|----------|----------|---------------------|
| 单个微服务崩溃 | 手动重启，Nacos 自动摘除故障实例 | ≤ 5 分钟 |
| 中间件故障（Redis/MySQL） | 手动重启 Docker 容器 | ≤ 10 分钟 |
| 服务器重启 | Docker Compose `restart: always` 策略自动恢复 | ≤ 3 分钟 |

### 4.3 数据持久化

- **MySQL**：Docker Volume 持久化存储，重启不丢失数据
- **Redis**：开启 AOF 持久化，防止重启后 Token 全部失效
- **Nacos**：> 📝 待补充（Nacos 嵌入式数据库或 MySQL 持久化方案）
- **MinIO**：Docker Volume 持久化，文件不丢失

## 5. 可扩展性需求

### 5.1 水平扩展能力

| 组件 | 可扩展性 | 扩展方式 |
|------|----------|----------|
| 业务微服务 | ✅ 可水平扩展 | 启动多个实例，Nacos 负载均衡 |
| API 网关 | ✅ 可水平扩展 | 多个 gateway 实例 + 前置负载均衡器 |
| Redis | ⚠️ 单节点限制 | 升级为 Redis Sentinel / Cluster |
| MySQL | ⚠️ 单节点限制 | 升级为主从复制 + 读写分离 |
| RabbitMQ | ⚠️ 单节点限制 | 升级为镜像队列集群 |

### 5.2 新服务接入规范

新微服务接入系统时，需满足以下要求：
1. **注册到 Nacos**：服务启动时自动注册，无需手动配置
2. **配置从 Nacos 读取**：所有配置通过 `${spring.application.name}.yaml` 从 Nacos 读取
3. **遵守 X-User-ID 规范**：从请求头获取用户身份，不自行解析 Token
4. **提供健康检查端点**：暴露 `/actuator/health` 端点

### 5.3 技术演进路径

| 当前方案 | 演进方向 | 触发条件 |
|----------|----------|----------|
| Docker Compose 单机部署 | Kubernetes 集群部署 | 需要多节点高可用 |
| 单数据库 | 分库分表（ShardingSphere） | 单表数据量超过千万 |
| 无搜索引擎 | 引入 Elasticsearch | 需要全文检索功能 |
| 无链路追踪 | 引入 Micrometer + Zipkin/SkyWalking | 服务数量增多，调试困难 |
